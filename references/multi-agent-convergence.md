# 多 Agent 协作与口径收敛

来源：2026 模拟赛 B 题（自来水厂 NTU 预测）的复盘教训——论文手 + 建模手 + 代码手 + Hermes + Codex 五方协作，却因「人肉总线、版本失控、口径不收敛」三件事共同翻车。适用于任何「多个队友 + 多个 AI」同时推进同一题的场景。

## 1. canonical 数据目录 + 版本号约定（防版本失控）

- 每一问的数据真源只允许一个目录、一个文件名，例如 `data/canonical_q1.csv`，其余一律视为派生版本。
- 派生文件必须带版本号与日期：`q1_v3_20260823.xlsx`，并附一行变更日志（谁、何时、改了什么口径）。
- 任何二手工作簿进论文/正式分析前，先跑 `scripts/data_fingerprint.py` 与 canonical 比指纹（行数、唯一时间键、非法时刻、目标列极值）；不一致即拒。
- 反例：本次 4380/4368/4370/4374 四个行数并存，多 Agent 在多个版本上各自建模，直到终局才统一到 4370。

## 2. 口径冲突的仲裁规则（防各自为政）

- **声明优先**：每个 Agent 产出数字时，必须写明口径（训练/验证/测试边界、评价指标定义、锚点选择、是否含泄漏）。
- **冲突必须显式列出**：发现两个 Agent 对同一量给出不同结论时，不得沉默二选一；要把「A 口径 vs B 口径 → 各自数字 → 差异根因」写清楚再选。
- **交付口径是最终裁决者**：选型/验证口径若与交付任务不同构（如「任意时刻锚平均」vs「交付日固定锚前推」），以交付口径为准，其余并列报告。详见 SKILL.md 阶段 8 第四条硬规则。
- 反例：本次代码手 workbook 写「以五折平均 RMSE 选用 Persistence」，Hermes 用交付口径测出 Δ 模型全胜，两边各守己见、无人裁决，论文采了错的那边。

## 3. 队友任务单格式（防「人肉总线」信息损耗）

给代码手/建模手的任务单，按「可直接转发 + 红线清单」格式写：

1. 目标（一句话）；
2. 必须做的事（可核验的动作，附验收标准）；
3. **明令禁止**（红线清单：不得删极端值、不得随机 K 折、不得改名 R²、不得用测试集调参…）；
4. 交付物与文件名约定；
5. 数据/口径来源指向（哪个文件、哪个 sheet）。

原则：**最小改动、只删不添**；用户要的是能直接转发的任务单 + 红线清单，不是更多分析。

## 4. 分工与验收

- 谁写代码谁负责可复现（requirements + 一行运行命令 + 随机种子）；谁引用数字谁先跑指纹/复算。
- 每个 Agent 的结论是**自述不是事实**；对外部副作用（上传、落盘、发布）要求可核验句柄（路径/ID），并读回验证。
- 跨 Agent 审计时，对前一 Agent 开出的「药方」必须自己实现跑一遍再采信（见 out-of-sample-evaluation-and-drift.md 第 5 节）。

## 5. 一句话

多 Agent 的价值在冗余交叉验证，风险在口径各说各话。用「canonical 目录 + 版本号 + 口径仲裁 + 任务单红线清单」四件套把冗余变成可靠、把各说各话变成显式冲突。
