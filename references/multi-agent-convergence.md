# 多 Agent 协作与口径收敛

来自 2026 模拟赛 B 题的协作复盘。以下方法适合出现多版本、交付口径冲突或反复交接的任务，按实际规模选用。

## 1. canonical 数据目录 + 版本号约定（防版本失控）

- 为每个数据源记录权威版本和位置。不同输入可以分别有权威版本；对派生文件记录源版本、变换和输出版本。
- 同口径的单时间键工作簿可用 `scripts/data_fingerprint.py` 对齐键和一个指定数值列。成功只证明所查范围一致；不一致或无法检查时不得主张两表等价。批准的派生表核验其变换、输入和实际使用的字段，不强求与原表逐值相等。
- 反例：本次 4380/4368/4370/4374 四个行数并存，多 Agent 在多个版本上各自建模，直到终局才统一到 4370。

## 2. 口径冲突的仲裁规则（防各自为政）

- **声明优先**：每个 Agent 产出数字时，必须写明口径（训练/验证/测试边界、评价指标定义、锚点选择、是否含泄漏）。
- **冲突必须显式列出**：发现两个 Agent 对同一量给出不同结论时，不得沉默二选一；要把「A 口径 vs B 口径 → 各自数字 → 差异根因」写清楚再选。
- **按交付设计选型验证**：在匹配交付口径的验证上选型，另留不参与选型的数据评估表现。不同口径分开报告；不要为了符合交付场景而拿冻结测试结果反向选型。详见 `out-of-sample-evaluation-and-drift.md`。
- 反例：本次代码手 workbook 写「以五折平均 RMSE 选用 Persistence」，Hermes 用交付口径测出 Δ 模型全胜，两边各守己见、无人裁决，论文采了错的那边。

## 3. 队友任务单格式（防「人肉总线」信息损耗）

给代码手/建模手的任务单，按「可直接转发 + 红线清单」格式写：

1. 目标（一句话）；
2. 必须做的事（可核验的动作，附验收标准）；
3. 本题不可越过的验证和数据边界，例如不得用未来信息构造预测特征、不得用冻结测试调参；
4. 交付物与文件名约定；
5. 数据/口径来源指向（哪个文件、哪个 sheet）。

用户要求可直接转发时，给简洁任务单；具体限制依据题意、数据结构和实际授权确定。

## 4. 分工与验收

- 明确结果生成者与复核者。保留可重跑入口、依赖与适用的配置；引用数字时核对相应的输出和计算口径。
- 每个 Agent 的结论是**自述不是事实**；对外部副作用（上传、落盘、发布）要求可核验句柄（路径/ID），并读回验证。
- 如果结论依赖某项修正，用可获得的运行结果或最小独立对照核验；没有证据的方案保留为建议。

## 5. 一句话

多 Agent 的价值在冗余交叉验证，风险在口径各说各话。用「canonical 目录 + 版本号 + 口径仲裁 + 任务单红线清单」四件套把冗余变成可靠、把各说各话变成显式冲突。
